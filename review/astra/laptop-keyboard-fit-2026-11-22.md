# Keyflame PR #77 review

The guide keyboard fits the two requested laptop viewports (1366 × 625 and 1280 × 600 CSS px) in the first lesson, a four-lane solo race, and a six-lane class race. I would fix keyboard access and preserve Bigger text before relying on compact mode for scaled laptops.

1. **Bug — the guide still goes below the fold at common scaled sizes.** `src/styles.css:341–360`, `scripts/check-overflow.mjs:36–42,143–149`. At 1093 × 500 (roughly 125% zoom on the reported viewport), the first lesson’s keyboard ended at y=522 and a six-lane class race at y=504. At 911 × 417 (roughly 150%), solo race, class race, and lesson ended at y=452, 504, and 522. The 24px lane minimum plus the lane borders and gaps exceed the allotted track budget as the screen gets shorter. The height breakpoint also reverses the improvement for a class race: at 800px the keyboard ended at y=766, and at 801px it ended at y=866. Size the track from the space left after reserving the typing panel, including gaps and borders. At very short heights, bound the opponent list and keep the player lane, prompt, and guide visible. Cover scaled CSS viewports and the 800/801 boundary with the six-lane fixture. The current fit assertion also accepts a hidden keyboard's zero-size rect, so assert that the spacebar is visible.
2. **Bug — Bigger text stops enlarging the typing prompt in compact mode.** `src/styles.css:46,355`. At 1366 × 625 the prompt was 22.5px both with and without the setting. At 801px it grew to 38px, and the lesson keyboard extended below the fold. The compact rule assigns a local `--type-size` directly on the prompt, overriding the inherited accessibility setting. Preserve a separate large-text prompt size, budget for the larger lines, and let the race scenery or opponent list yield space first.
3. **Bug — keyboard-only players cannot reach the in-play toggle.** `src/ui/typingView.ts:155–167,335–352`. Tab skipped it throughout the lesson. Make the native button tabbable and let Enter/Space activate it when it has focus. Have the document typing handler ignore those activation keys on focused interactive controls so a Space press can never both type and activate. Keep the short Show/Hide wording as an action label and use `aria-controls` to point to the guide. If using `aria-pressed`, use a stable label such as “Keyboard guide.” The current location next to the finger cue is relevant, but the button is visually secondary. Give it a consistent position immediately above the guide, including while the guide is hidden. Discoverability for children remains untested.
4. **Should fix — “real keyboard” and “fine primary pointer” can disagree on hybrids.** `src/styles.css:341`, `src/ui/app.ts:214–219`, `src/ui/typingView.ts:320–331,359–360`. A Windows touchscreen laptop reporting a fine hovering primary pointer takes the compact branch when it uses physical-keyboard mode, which is the intended layout. If the primary pointer reports coarse, typing switches the app to keyboard mode while the compact query stays off. In touch-first Chromium emulation at 1366 × 625, the guide ended at y=731 after typing a real key and reopening the lesson. The original in-progress screen drops the pinned keyboard and has no toggle until reentry. Ordinary iPad-style touch emulation stayed pinned and outside the compact branch until a hardware key, as expected. On reentry the same tablet got a toggle and its guide extended 20px below the viewport. Define the behavior for touch-first hardware-keyboard users explicitly and use the same capability decision for the guide and toggle. If the compact layout must stay desktop-only, include a tested desktop/hybrid signal and keep the ordinary touch layout intact. Test a Windows convertible and an iPad with a trackpad on-device.

Clicking Hide set the keyboard's hidden state and Show restored it. The preference survived reloading and reopening the lesson both as a guest and as a saved rider. The toggle uses the existing per-rider save path. An older saved false value now hides the guide, as specified.

Verification used PR head `ae02bb8`, Chromium 153 with CSS viewport sizes and emulated input capabilities, and a fixture with five displayed classmates plus the player out of 30 total riders. The build, all 280 unit tests, and the repository’s Chromium overflow check (20 screens at 15 sizes) passed. Windows display scaling, physical Safari/iPad hardware and real children were outside the test setup. The 125% and 150% results use equivalent viewport dimensions.

## Tablet checks

- Touch-only Chromium emulation covered the iPad mini, 10.2-inch iPad, iPad Air, 12.9-inch iPad Pro, and an Android tablet at 800 × 1280 CSS px, each in portrait and landscape. The race and first lesson kept the tap keyboard pinned to the viewport in all ten cases, with zero horizontal overflow. The desktop compact rules and toggle stayed inactive. A saved Hide preference for the desktop guide still allowed the pinned touch keyboard when returning to touch mode.
- In Auto mode, a physical key press removed the pinned keyboard without adding the guide or its toggle to the active lesson. On reopening, the guide and toggle appeared at every size. The iPad mini landscape was the only one where the reopened guide needed scrolling (keyboard bottom y=764 on a 744px viewport).
- A fine-pointer desktop proxy at 1133 × 744 and 640 × 744 matched compact mode. Its race and lesson guides fit and Hide worked. This shows what happens when the query reports a fine hovering primary pointer. It does not establish how iPadOS Safari reports a Magic Keyboard or an external trackpad.
